kiro2api 精确记账：数据怎么流

opus-5.5 的请求现在按精确数字记账：输入（prompt）由网关自己用 Claude 分词器数出来，输出 = 上游给的总数 − 输入，缓存读/写按上游扣的 credits 反推。 判断标准：同一会话里本轮读到的缓存应等于上一轮的 prompt。11-09 09:05 上线的版本在一个新会话的 11 对连续请求上做到 0 到 1 个 token 的差。

上游给的数 网关精确算的数 从 credits 推的数 退回估算的情况

一张图

① 发出前：数 prompt把发给 Kiro 的请求体（历史消息、工具列表、工具调用和结果、图片）按上游的渲染格式拼成文本，用移植的 ctok 分词器数 token，再加实测的框架常数。
→
② 上游返回Kiro 不给 token 数，只给两样：
总数 T = round(上下文占比 × 1,000,000)，以及本次扣的 credits。
→
③ 输出输出 = T − prompt。
这个数包含看不见的 thinking，因为 T 本身就含。
⑤ 记下 thinking 的 token本次 thinking 签名对应的 token = 输出 − 可见部分（文本＋工具调用），连同签发时的上下文（工具列表＋之前全部消息的哈希）存进 SQLite 表 reasoning_tokens。客户端下回把这段 thinking 带回来时查表；上下文变了的签名上游会忽略，网关也不算。
←
④ 缓存读/写Kiro 收两种价里便宜的那种：
读价×读 + 写价×写，或 未缓存价×整个 prompt。
按前一种收时解出读和写；按后一种收时 credits 看不出缓存。
退回估算按未缓存价收费（冷请求、新增内容超过 prompt 约 30%）、prompt 里有查不到的签名、读不出尺寸的图片、非 opus-5.5 模型、缺 credits 时，这一条的读写按旧的缓存跟踪器估算，记为 local。

逐步看

每一步用什么方法、产出什么

步骤方法产出
数 promptctok v4.8 分词器（开源，MIT）移植成 TypeScript；工具列表按 <functions> + 排序键 JSON 渲染，工具调用按 function_calls / invoke / parameter 渲染，工具结果按 function_results 渲染；图片按 28 px 一格算格数 + 3。prompt token 数，及“是否含估值”标记
框架常数在真实上游上发探针请求测出：Kiro 自带系统提示 1889；每条历史消息 +2；工具列表外壳 +277；每次回复结尾 +2；还有工具调用、工具结果、空结果、并行调用各自的常数。带回的 thinking：纯文字回复带推理 +2，第一次推理之后不紧跟工具结果的纯文字回复也 +2，带工具调用的回复只算推理本身。工具名：回放的一次调用里上游只按真名收一处，另一处是固定开销，所以工具结果一律按 Bash 的名字数（以前按真名数，Read 每次少 1、ToolSearch 多 3、MCP 工具多 9 左右）。70 个探针全部做到与上游的 prompt 一个 token 不差（带推理的用原样重发的 credits 反解真实 prompt）
输出T − prompt含 thinking 的真实计费输出
缓存拆分实测单价（credits/token）：读 3.319979e-6，写 3.316302e-5，未缓存 1.227197e-5，输出 2.210225561e-4。credits = 输出价×输出 + min(读价×读 + 写价×写, 未缓存价×prompt)。按前一种收时：读 = (写价×prompt − (credits − 输出价×输出)) ÷ (写价 − 读价)。接着上一轮聊：读 = 上一轮 prompt − 约 3；原样重发同样只差约 3；探针上 26 个命中的请求全部在 ±1.3 token 内
thinking 记录签名的 sha256 当键，存它背后的 token 数和签发时的上下文哈希。上下文对不上（之前的消息或工具列表变了，例如 Claude Code 用 ToolSearch 加载了工具）就按 0 算，探针证明上游此时直接忽略这段推理。没见过的签名先按 (长度 − 620) ÷ 3.4 估一次并钉住，这一轮的误差会反向记进新回复的记录里，下一轮两者相加又等于上游的数。同一会话第二轮起恢复精确

实测（11-09 线上请求）

“上一轮 prompt − 本轮读”：0 表示完全对上；负数表示读得比上一轮 prompt 还多，说明本轮 prompt 少数了（少数 1 个 token，读就多出约 6 个）。

版本成对的连续请求上一轮 prompt − 本轮读说明
2cfd89e（两价模型）—几百到 2000 以上把新写的部分按未缓存价算，读少了约 2.3 倍的新增内容
7978e6e（三价模型）24中位 −8，大多 −40 到 +22还剩工具名按真名数两遍的误差
6625240（工具名修正）17新会话 11 对：−1 到 +1；部署前开始的老会话 6 对：−12 到 −17老会话的 prompt 稳定少数 2–3 个，来源没查到

按未缓存价收的请求可以直接从 credits 反解 prompt：线上 15 条与网关计数差在 ±2.6 以内。

还不精确的地方

情况为什么怎么处理
部署前就存在的 thinking 签名当时没记下它背后的 token 数第一次见到时估一次并钉住，该会话下一轮恢复精确
opus-5.5 以外的模型框架常数和分词器只在 opus-5.5 上测过继续用旧的估算
按未缓存价收费的请求Kiro 这时按整个 prompt 的未缓存价收，credits 里没有缓存的信息读写按缓存跟踪器估，记为 local；prompt 和输出仍是精确的
Kiro 换了系统提示或客户端身份基础常数 1889 会变表现为 exact 行变少、输出出现负数；需要重新测
部署前开始的老会话一个 17 万 token 的会话每轮 prompt 都少数 2–3 个，请求体没留存，没法逐条对差值固定不累积，读写各偏 15 个左右
签名在上下文变了之后又跟着纯文字消息这种组合的框架开销没测按已测的规则算，可能差 2
读不出尺寸的图片文件头不是 PNG/JPEG/GIF/WebP按 1600 估，这条记为 local
