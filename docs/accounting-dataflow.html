kiro2api 精确记账：数据怎么流

opus-5.5 的请求现在按精确数字记账：输入（prompt）由网关自己用 Claude 分词器数出来，输出 = 上游给的总数 − 输入，缓存读/写按上游扣的 credits 反推。 上线后（11-09 07:40 起）30 条请求里 21 条是精确记账，这 21 条用三个单价重算出的 credits 与上游实扣的差都在 1% 以内；其余 9 条退回旧的估算。

上游给的数 网关精确算的数 从 credits 推的数 退回估算的情况

一张图

① 发出前：数 prompt把发给 Kiro 的请求体（历史消息、工具列表、工具调用和结果、图片）按上游的渲染格式拼成文本，用移植的 ctok 分词器数 token，再加实测的框架常数。
→
② 上游返回Kiro 不给 token 数，只给两样：
总数 T = round(上下文占比 × 1,000,000)，以及本次扣的 credits。
→
③ 输出输出 = T − prompt。
这个数包含看不见的 thinking，因为 T 本身就含。
⑤ 记下 thinking 的 token本次 thinking 签名对应的 token = 输出 − 可见部分（文本＋工具调用）。存进 SQLite 表 reasoning_tokens，客户端下回把这段 thinking 带回来时直接查表。
←
④ 缓存读/写credits = 写价×写 + 读价×读 + 输出价×输出，
写 + 读 = prompt。两个方程解出读和写。
退回估算prompt 里有查不到的签名、读不出尺寸的图片、非 opus-5.5 模型、缺 credits 时，这一条按旧的缓存跟踪器估算，记为 local。

逐步看

每一步用什么方法、产出什么

步骤方法产出
数 promptctok v4.8 分词器（开源，MIT）移植成 TypeScript；工具列表按 <functions> + 排序键 JSON 渲染，工具调用按 function_calls / invoke / parameter 渲染，工具结果按 function_results 渲染；图片按 28 px 一格算格数 + 3。prompt token 数，及“是否含估值”标记
框架常数在真实上游上发 33 个探针请求测出：Kiro 自带系统提示 1889；每条历史消息 +2；工具列表外壳 +277；每次回复结尾 +2；还有工具调用、工具结果、空结果、并行调用各自的常数。33 个探针全部做到 prompt + 可见输出 = 上游 T，一个 token 不差
输出T − prompt含 thinking 的真实计费输出
缓存拆分实测单价（credits/token）：写 1.227197e-5，读 3.31675e-6，输出 2.210225561e-4。读 = (写价×prompt + 输出价×输出 − credits) ÷ (写价 − 读价)。冷请求读 = 0；原样重发时只有 13 个 token 没命中缓存
thinking 记录签名的 sha256 当键，存它背后的 token 数。没见过的签名先按 (长度 − 620) ÷ 3.4 估一次并钉住，这一轮的误差会反向记进新回复的记录里，下一轮两者相加又等于上游的数。表里现有 306 条；同一会话第二轮起恢复精确

还不精确的地方

情况为什么怎么处理
部署前就存在的 thinking 签名当时没记下它背后的 token 数第一次见到时估一次并钉住，该会话下一轮恢复精确
opus-5.5 以外的模型框架常数和分词器只在 opus-5.5 上测过继续用旧的估算
Kiro 换了系统提示或客户端身份基础常数 1889 会变表现为 exact 行变少、输出出现负数；需要重新测
读不出尺寸的图片文件头不是 PNG/JPEG/GIF/WebP按 1600 估，这条记为 local
